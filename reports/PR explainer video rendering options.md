# Keep Chromium, borrow Shiki, test HyperFrames

As of 2026-10-05, no renderer found beats the current engine on the dimensions that matter, and the most promising moves are narrow. Three categories fail the hard requirement of exact on-screen strings, or fail on cost and control: generative video models (best glyph correctness 58.2%, nothing tested on code), hosted JSON-to-video APIs ($0.05-$0.25 per minute, their own templates), and Manim (Python scripts, no diff scene). That leaves deterministic renderers that draw the strings they are given. Among those, only **HyperFrames** (HeyGen, Apache-2.0, created 2026-03-10, v0.8.133 on 2026-10-05) is both a whole renderer and the same architecture as ours (headless Chrome stepped frame by frame, then ffmpeg), with native JSON variables and built-in `code-diff` and `code-morph` blocks. **Remotion** (4.0.533, 2026-10-05) is the most mature host and pairs with Code Hike for frame-deterministic code morphs, but its license is source-available and free only up to 3 employees. The single most valuable and cheapest upgrade is a library, not a renderer: Shiki 4.5.0 (2026-10-01, MIT) with its Decorations API, plus the keyed-token machine from `@shikijs/magic-move` 4.5.0 (2026-10-01, MIT), dropped into the existing engine. Browser-free Rust and Python renderers (fframes, skia-python harnesses, MotionGram) are the only route to a real speed or install-size gain, but no source measured them on our workload. Every speed figure in the notes comes from a single author or a vendor on unspecified hardware, so the bakeoff is the first real measurement. The baseline (75-105 s per 55-72 s video, free, already in a Python CLI) is already about as fast as the best-reported framework number.

## Only deterministic renderers survive the exact-text gate

Generative video is out for this job. The VidScribe preprint (submitted 2026-09-29) scored seven commercial models on rendering supplied text and found content accuracy averaging 82.7% but glyph correctness below 60%: Seedance 2.5 at 58.2, MiniMax H3 at 57.0, Kling3.0-Omni at 43.8 ([arXiv 2609.36598](https://arxiv.org/abs/2609.36598)). Image-to-video preserved text best (82.2% task mean) and video-to-video editing worst (65.6%), and in-place text edits corrupted neighboring text. No benchmark in the notes covers multi-line code. Cost compounds the problem: Veo 3.1 Lite is $4.80 per 60 s at 1080p and Veo 3.1 Standard $24.00, but clips cap at 8 s, so a video needs about 8 stitched generations before any retries ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing), [Veo docs](https://ai.google.dev/gemini-api/docs/veo)). Sora's API sunset date of 2026-09-24 has passed ([CostGoat](https://costgoat.com/pricing/sora)). The only hybrid that keeps text exact is an AI background with a deterministic text layer on top; the notes found no evidence it improves reviewer comprehension, and the closest comprehension evidence, Code2Video's TeachQuiz, favors code-rendered output over pixel generation ([arXiv 2510.01174](https://arxiv.org/abs/2510.01174)). Avatars ($3-9 per minute, e.g. HeyGen Avatar IV at $3/min) add a face the checker cannot verify ([Anam](https://anam.ai/blog/heygen-pricing)). Hosted JSON-to-video services price at $0.05-$0.25 per 60 s (Shotstack 5-20 cents per minute, json2video about $0.25 at the Professional rate) but render their own templates, so a syntax-highlighted diff and check.py guard would not carry over ([Shotstack](https://shotstack.io/pricing/), [json2video](https://json2video.com/pricing/)).

Within the window, several well-known tools are also stale or the wrong shape. Motion Canvas's last stable release is 3.17.2 (2024-12-14) and its last alpha 2025-02-16 ([npm registry](https://registry.npmjs.org/@motion-canvas/2d)). Revideo shipped 0.11.0 on 2026-07-10 but its maintainers say engine improvements now go to the commercial Midrender product first ([midrender.com/revideo](https://midrender.com/revideo)). Slidev (53.0.0, 2026-09-16) and reveal.js export PDF/PNG, not video ([Slidev exporting](https://sli.dev/guide/exporting.html)). Snappify exports video only from an experimental desktop app ([Snappify](https://snappify.com/features/video-export)). Manim Community (0.21.0, 2026-08-10, MIT) is scripted in Python, tokenizes with Pygments, documents no diff or range highlight, and its only documented speed gain is 2.2x on its own benchmark ([changelog](https://docs.manim.community/en/stable/changelog/0.21.0-changelog.html), [code_mobject.py](https://raw.githubusercontent.com/ManimCommunity/manim/main/manim/mobject/text/code_mobject.py)). Takumi has strong text shaping but its only Python binding is GPL-3.0 and self-described as not production-ready ([takumi-py](https://github.com/BalconyJH/takumi-py)). Lottie and Rive renderers animate pre-authored artboards, which makes per-token code diffs a poor fit.

HyperFrames is the nearest cousin: the same stepped-Chrome-plus-ffmpeg pipeline, the same HTML authoring, and a published `--variables` interface that maps almost directly to a board file. It also ships `lint` and `check` commands and Docker rendering for controlled CI ([rendering guide](https://hyperframes.mintlify.app/guides/rendering)). The cost is churn and maturity: it is still 0.x, ships several releases per day, and its star count reportedly jumped from about 14,000 in July to 57,105 in October, which says more about promotion than reliability ([ArceApps](https://arceapps.com/blog/hyperframes-vs-remotion-2026/), [GitHub API](https://api.github.com/repos/heygen-com/hyperframes)). Its `code-morph` block runs Shiki Magic Move as a paused GSAP timeline with tokens baked to JSON, but the shipped version has three hardcoded states and no parameters, so it is a pattern to copy more than a drop-in ([Code Morph](https://hyperframes.heygen.com/catalog/blocks/code-morph)). Adopting it would also add Node 22+ for end users of a Python CLI, and it gives no speed advantage worth the swap: our 1.4x-real-time baseline is on par with its 1.55x. The best structural evidence for the approach is that the two closest public PR-video tools, `pr-walkthrough` (HyperFrames, JSON manifest with `diff` slides and a `focus` scroll, 1280x720 output) and `shipreel` (MIT, created 2026-09-30), also use headless Chrome and ffmpeg ([SKILL.md](https://raw.githubusercontent.com/ilamanov/skills/main/.agents/skills/pr-walkthrough/SKILL.md), [shipreel](https://raw.githubusercontent.com/theBstar/shipreel/main/README.md)). Neither mentions a deterministic text verifier, which is the differentiator we already own.

Remotion is the safest host for token morphs because the Code Hike template applies precomputed keyframes with `interpolate(frame, ...)`, which is frame-deterministic ([CodeTransition.tsx](https://raw.githubusercontent.com/remotion-dev/template-code-hike/main/src/CodeTransition.tsx)). Two catches matter for a CLI that ships to others. First, the license is per using company: if our CLI bundles Remotion, any end user at a company above 3 employees would need their own Company License, and the notes do not settle whether our distribution counts as the "automation" the Automators tier covers; that needs a read of the primary text before any commitment (inference). Second, the terms page is labelled v5.0, which is unreleased and adds mandatory license-key telemetry for company licenses ([v5 migration](https://www.remotion.dev/docs/5-0-migration)); whether those exact thresholds apply to 4.0.x was not confirmed, and PkgPulse's "BUSL for companies over $1M ARR" contradicts Remotion's own page, so the primary source wins ([PkgPulse](https://www.pkgpulse.com/guides/remotion-vs-motion-canvas-vs-revideo-programmatic-video-2026)). Remotion also renders slower in the only comparisons found, though by a single blogger on unspecified hardware.

## Libraries can modernize the code scenes without replacing the engine

Because the baseline already drives Chromium frame by frame, the code-diff and morph quality gap closes with libraries that return data rather than pixels. **Shiki 4.5.0** (2026-10-01, MIT, about 600 KB plus grammars and themes) tokenizes with TextMate grammars, and its Decorations API wraps character or line ranges with classes "without modifying the source text itself", which is the cleanest way to feed highlight ranges from board JSON while keeping the string check.py guards ([npm registry](https://registry.npmjs.org/shiki), [Shiki decorations](https://shiki.style/guide/decorations)). By contrast, Shiki's comment-notation transformers (`[!code ++]`) strip annotation comments from the output, so they alter on-screen text ([transformers](https://shiki.style/packages/transformers)). **`@shikijs/magic-move` 4.5.0** (2026-10-01, MIT, about 81 KB) exposes `codeToKeyedTokens()` and `createMagicMoveMachine()` as a framework-agnostic keyed-token diff built on `diff-match-patch-es`; the standalone repo was archived 2026-06-03 and folded into the Shiki monorepo ([README](https://github.com/shikijs/shiki-magic-move), [npm](https://registry.npmjs.org/@shikijs/magic-move)). Its stock DOM renderer is wall-clock driven (CSS transitions and `animation.finished`), so it is not seekable per frame; we would reuse the machine and apply the positions ourselves, exactly as HyperFrames does with a paused timeline ([renderer.ts](https://raw.githubusercontent.com/shikijs/shiki/main/packages/magic-move/src/renderer.ts)).

**Code Hike 1.1.0** (2026-03-17, MIT) offers `calculateTransitions`, which returns per-element keyframes that a host can apply at any frame, but its `highlight()` strips default `!`-prefixed annotation comments from the code and it depends on a 9 MB tokenizer, `@code-hike/lighter`, last published 2024-12-31 ([npm](https://registry.npmjs.org/codehike), [highlight.ts](https://raw.githubusercontent.com/code-hike/codehike/main/packages/codehike/src/code/highlight.ts), [token-transitions.tsx](https://raw.githubusercontent.com/code-hike/codehike/main/packages/codehike/src/utils/token-transitions.tsx)). A real `// !important` comment could be silently removed unless `annotationPrefix` is changed; this is inferred from the source and untested. **`@pierre/diffs` 1.5.1** (2026-09-25, Apache-2.0, 7.4 MB unpacked) renders split or stacked Shiki-based diffs with inline word highlighting and line selection as HTML that a headless browser can capture, but it does not animate and SSR support is unconfirmed ([npm](https://registry.npmjs.org/@pierre/diffs), [README](https://raw.githubusercontent.com/pierrecomputer/pierre/main/packages/diffs/README.md)). The check that makes any of these safe is cheap and independent of the library: join the token text on each line and compare it to the diff line from the board. The notes recommend it but nobody ran it, including for tabs, CRLF and trailing newlines. Shiki moves fast (4.5.0 on 2026-10-01), so pin versions: token output and therefore morph keys can change between releases. Tokens can also be baked to JSON at storyboard-build time, as `code-morph` does, which would keep Node off end-user machines (inference).

## Browser-free renderers promise speed, but no one measured them

The only credible route to a materially faster or smaller pipeline is leaving Chromium, and the evidence there is thin. **fframes** (Rust, MIT, v1.2.0 on 2026-10-03, 2,090 stars) is the most credible: Skia, prebuilt Skia and FFmpeg downloads, a CPU fallback documented as slower than its GPU backend, and a launch video of 128 s "rendered in 36 seconds" on unspecified hardware, with GPU about 10x faster than CPU ([fframes](https://github.com/dmtrKovalenko/fframes), [README](https://raw.githubusercontent.com/dmtrKovalenko/fframes/main/README.md)). Scenes are Rust functions returning SVG trees with no JSON input, so a Rust shim over the board would be required. A pip-installable Python harness is the other path: skia-python 144.0.post2 (BSD, wheels for Linux and macOS, Linux needs libEGL, OpenGL and fontconfig) or resvg-py rasterize per-frame SVG built from board JSON, with frames piped to ffmpeg ([PyPI skia-python](https://pypi.org/pypi/skia-python/json), [resvg-py](https://pypi.org/pypi/resvg-py/json)). Pillow's vendored libraqm gives HarfBuzz shaping and ligature control for monospace code ([Pillow docs](https://pillow.readthedocs.io/en/stable/reference/ImageFont.html)). **MotionGram 0.5.0** (MIT, uploaded 2026-10-04) is the closest ready-made match, with YAML manifests, Skia, Typst and PyAV, but it is pre-alpha and day-one, so it is a reference design, not a dependency ([PyPI](https://pypi.org/project/motiongram/0.5.0/)). rust-motion/dioxuscut takes JSON props with a Python wheel but has 3 stars and was created 2026-07-14 ([repo](https://github.com/sjkim1127/rust-motion)). Exactness is a mild advantage for the glyph-drawing options because they bypass browser text rasterization, but whether OCR accuracy improves over Chromium at GitHub inline-player width is an open question for the bakeoff. DOM-based options also render with whichever fonts the capture machine has, and macOS and Linux antialiasing differ; no measured difference was found, so the OCR gate should run on both.

## Bakeoff shortlist and what it costs

The shortlist has four entries: two whole renderers, one library set, and one browser-free wildcard. The baseline runs as the control. All four render the same two scenes from `boards/mdp12.json` (groups before/after, and a code diff), take their strings only from the board, and are scored on the stated criteria with the OCR check against check.py receipts as a hard gate: a contender that fails it on either scene is out regardless of speed. Run the OCR gate at full 1920x1080 and again at the actual width of the GitHub inline player, which the notes did not measure; `pr-walkthrough`'s 1280x720 downscale is one precedent. Run render timing on the Mac and on Linux CI, record install size, and strip identities before the blind side-by-side frame comparison.

Treat the library set as the control's upgrade, not a rival: it is the only entry that keeps the current speed, install story and license while improving code scenes, and it is a candidate to win alone or to combine with any renderer. Entry 4 carries the weakest evidence and is included for the one thing the others cannot offer, a possible escape from Chromium startup and screenshot cost; if its Rust shim proves heavier than the scenes warrant, replace it with the Python harness rather than expanding the set. Excluded and why: Manim, Motion Canvas and Revideo (stale, scripted or roadmap-captured), Slidev, reveal.js and Snappify (no headless video path), every hosted API and AI video model (fail the OCR gate or cost per video by design), Takumi (GPL binding), and Lottie and Rive (pre-authored artboards).

## Conclusion

The notes show that the market has converged on our architecture, not away from it: the closest PR-video tools and HyperFrames all step headless Chrome and encode with ffmpeg, and the only published head-to-heads show a swap would match our speed at best. What is new in 2026 is not a better renderer but better parts: Shiki's text-preserving Decorations, a framework-free keyed-token morph machine, and a published pattern (HyperFrames' paused timeline) for making morphs seekable. Our deterministic check.py is the differentiator in a field where verification is absent, which argues for protecting it over chasing a framework.

What this leaves unknown is exactly what the bakeoff should answer: no source measured any option at 1080p30 on our scenes, no source tested OCR accuracy of rendered code at inline-player width, and Remotion's license applicability to a distributed CLI is unsettled. If entry 3 passes the gate and entries 1 and 2 add nothing measurable, the right outcome is to keep the engine, upgrade its code scenes, and stop.
