How the morning report writes into a Google Doc

A daily workflow reconciles LinkedIn connections into Supabase, then writes the result into a private Google Doc. This page lets you step through the two parts a reviewer needs.

1. Writing into the Doc

Before the run. The test Doc has a note, a begin marker, the text old, an end marker and a second note. See e2e_doc_report.py:24.

Find the markers. The reporter owns only the text between the two markers. It needs exactly one of each, as plain paragraphs in one tab.

Remove the old text. Whatever sat between the markers goes. The real update is one batch request; this figure splits it in two so you can see each half.

Write the report. The new text is the status, the run time, the six counts and a next action, built by render_report at google_doc_report.py:73.

Leave the notes alone. The note above and the note below the markers stay the same. The test checks both ends of the Doc at e2e_doc_report.py:237.

2. The order of work in run()

Google first. The script checks the Doc before it reads LinkedIn or writes to Supabase. A shared Doc stops the run here, before any other work.

LinkedIn fails. A LinkedIn API error gives the status BLOCKED. The script still publishes that status to the Doc.

Something else fails. Other errors after the LinkedIn client starts usually give FAILED. If the client never started, the status is BLOCKED.

3. What changed
